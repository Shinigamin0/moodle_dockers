Read/Write Splitting en
Moodle 5 con MySQL GTID

Demostración de que una instancia Moodle configurada como nodo API enruta automáticamente las lecturas a una réplica MySQL y las escrituras al master, con evidencia verificable a través de mysql.general_log.

✓ Validado en producción local Moodle 5.0.2 MySQL 8.4.10 Docker · Ubuntu 24.04 2026-07-01
01

Resumen ejecutivo

Este POC demuestra la viabilidad de un esquema de separación de carga de base de datos para una plataforma Moodle de alta demanda. La arquitectura consiste en un nodo principal que concentra todas las operaciones de escritura, y un nodo API —dedicado al consumo de servicios— que redirige automáticamente todas sus lecturas hacia una réplica MySQL sincronizada en tiempo real.

El mecanismo es nativo de Moodle 5: la configuración $CFG->dboptions['readonly'] en config.php instruye al DBI interno para enrutar queries sin modificar una sola línea de código de la aplicación.

✓
Resultado verificado: el usuario readonly generó 1.180 queries en la réplica — todas SELECT — con cero escrituras directas. La replicación GTID opera con latencia inferior a 1 segundo.

04

Mecanismo de Read/Write Splitting

Moodle 5 incluye soporte nativo para réplicas de lectura a través de la clave $CFG->dboptions['readonly'] en config.php. Cuando esta configuración está presente, el DBI de Moodle establece dos conexiones distintas: una al master para escrituras y una a la réplica para lecturas — sin requerir ningún cambio en el código de plugins o módulos.

Configuración en config.php del nodo API

PHP config.php (api_app) 
// ================================================================
// Debe estar ANTES del require_once de lib/setup.php
// Moodle inicializa la conexión DB al cargar setup.php,
// si el bloque viene después, es ignorado.
// ================================================================
$CFG->dboptions['readonly'] = [
    'instance' => [
        [
            'dbhost' => 'api_db',        // hostname del contenedor réplica
            'dbport' => '3306',
            'dbuser' => 'readonly',    // usuario con solo SELECT
            'dbpass' => 'Password'
        ]
    ]
];

// Desactivar logs de Moodle para el nodo API (solo lectura de datos)
$CFG->disablelog = true;
$CFG->disableupdatelogin = true;

// Este require_once DEBE venir después del bloque readonly
require_once(__DIR__ . '/lib/setup.php');
⚠
Punto crítico: el bloque $CFG->dboptions['readonly'] debe colocarse antes del require_once(__DIR__ . '/lib/setup.php'). Moodle inicializa la conexión a la base de datos cuando carga setup.php; cualquier configuración posterior es ignorada silenciosamente.

Comportamiento del DBI de Moodle

Tipo de operaciónConexión usadaContenedorUsuario DB

INSERT / UPDATE / DELETE Master (principal) principal_db user
DDL (CREATE, ALTER) Master (principal) principal_db user
05

Replicación MySQL con GTID

La sincronización entre principal_db y api_db usa GTID (Global Transaction Identifiers), el modo de replicación recomendado para MySQL 8.x. Cada transacción recibe un identificador global único; la réplica solicita automáticamente las transacciones que le faltan usando SOURCE_AUTO_POSITION=1.

Configuración de replicación

MySQL Ejecutado en api_db al inicializar 
-- Vincular la réplica al master (ejecutado una sola vez en deploy)
CHANGE REPLICATION SOURCE TO
    SOURCE_HOST    = 'principal_db',
    SOURCE_USER    = 'replicator',
    SOURCE_PASSWORD= 'repl_password',
    SOURCE_AUTO_POSITION = 1,   -- modo GTID automático
    GET_SOURCE_PUBLIC_KEY = 1;  -- RSA key exchange para auth

START REPLICA;

Parámetros del master

Bash Flags de inicio del contenedor principal_db 
docker run ... mysql:8.4.10 \
  --server-id=1 \
  --log-bin=mysql-bin \
  --enforce-gtid-consistency=ON \
  --gtid-mode=ON
ℹ
Las entradas skip-grants user que aparecen en los logs de api_db son normales: corresponden a los BEGIN/COMMIT de los threads internos de replicación GTID. No son errores ni accesos externos.

Usuarios de base de datos

replicator REPLICATION SLAVE Thread de replicación GTID No aplica

ℹ
Los usuarios user y readonly son creados en principal_db y se replican automáticamente a api_db gracias a GTID. No es necesario crearlos manualmente en la réplica.

Guía de despliegue paso a paso

ℹ
El despliegue completo toma aproximadamente 5-7 minutos. La mayor parte del tiempo la ocupa la instalación de Moodle via CLI (creación de tablas, defaults, plugins).
1
Construir la imagen Moodle

La imagen base es Ubuntu 24.04 con PHP 8.4, Apache2 y Moodle 5.0.2. Solo se construye una vez; se reutiliza en ambos nodos.

Bash
cd moodle_dockers/images
./build_502.sh
2
Desplegar el ambiente completo

El script crea la red, levanta ambas bases de datos, configura la replicación, instala Moodle, crea usuarios y despliega ambos nodos de aplicación.

Bash
cd environments/mvp_moodle_api
./deploy.sh

Lo que hace deploy.sh internamente, en orden:

#Acción
1Crea la red Docker mvp_moodle_api_network
2Levanta principal_db (GTID ON, server-id=1)
3Crea usuario replicator en el master
4Levanta api_db (GTID ON, server-id=2)
5Vincula réplica al master con CHANGE REPLICATION SOURCE
6Activa general_log en ambos motores
7Levanta principal_app e instala Moodle via CLI
8Crea usuario readonly (SELECT en moodle.*)
9Genera config.php para el nodo API con bloque readonly antes de require_once
10Copia moodledata de instancia 1 a instancia 2
11Levanta api_app e inyecta config.php

Validación

Validar la replicación MySQL

Inserta un registro en el master y verifica que aparece en la réplica sin intervención manual:

Bash
./replication_test.sh

El script crea la base test_replicacion, inserta una fila en principal_db y la consulta en api_db. Si los datos aparecen en ambos, la replicación está activa.

Generar tráfico en el nodo API

Antes de revisar los logs, genera peticiones HTTP para que Moodle ejecute queries:

Bash
# Peticiones GET simples
for i in $(seq 1 5); do
  curl -s -o /dev/null -w "%{http_code}\n" http://localhost:81/
done

# Login para generar queries de sesión
curl -s -c /tmp/cookies.txt -b /tmp/cookies.txt \
  -L http://localhost:81/login/index.php \
  -d "username=admin&password=Admin1234!" -o /dev/null

Revisar los logs de ambos motores

Bash
./log.sh

El script consulta mysql.general_log en ambos motores y muestra las últimas 30 queries de cada uno ordenadas por timestamp.

Verificar el placement del bloque readonly

Si sospechas que el splitting no está activo, confirma la posición del bloque en config.php:

Bash
docker exec -i api_app grep -n "readonly\|require_once" /var/www/html/config.php

El número de línea del bloque readonly debe ser menor que el de require_once.
